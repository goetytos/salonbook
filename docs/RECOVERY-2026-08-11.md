## Schema reconciliation

The live schema contained the migration-003 changes, although
`schema_migrations` recorded only migrations 001 and 002. Migration 003 was
made idempotent so it can safely reconcile that history. Migration 004:

- preserves service name, original price, discount, and final price on bookings;
- prevents service deletion from cascading through booking history;
- protects active appointment overlaps at the database level;
- keeps promotion limits and price arithmetic internally consistent;
- enables RLS and revokes direct PostgREST access for application tables;
- supplies a narrow compatibility trigger for the pre-retouch booking writer;
- adds tenant/lookup indexes and validates lifecycle values.

Migration 005 removes the original global `(name, phone)` customer constraint
and replaces it with a passwordless-guest-only unique index. A customer can
therefore create a credentialed account beside an existing guest record, while
the recovered guest row and its bookings remain unchanged. Those records must
never be linked by name or phone alone; a future account-linking flow requires
verified phone ownership (for example, OTP) and an audited transactional merge.
